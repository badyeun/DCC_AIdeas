> 슬라이드를 만들 수 있도록, 용어 설명과 숫자 출처를 함께 적었습니다.

## 1. 과제와 평가 방식 (모델 설명 ①)

### 무엇을 푸는가

119 신고 통화의 **전사 텍스트만** 읽고, 환자에게 해당하는 증상을 9종 중에서
골라냅니다. 한 통화에 여러 증상이 동시에 있을 수 있습니다(다중 라벨).

> 9종: 고열 · 구토 · 두통 · 복통 · 어지러움 · 열상 · 오심 · 전신쇠약 · 호흡곤란

음성 파일은 읽지 않습니다. 주석 JSON의 `utterances[].text`만 입력으로 쓰고,
speaker · 시간 · 성별 · 주소 · 중증도 등 **다른 라벨링 데이터는 쓰지 않았습니다**
(출제문제 9쪽 "전사 텍스트 외 라벨링데이터 사용 불가").

### 데이터

| | 통화 수 |
|---|---:|
| Training (서울) | 29,200 |
| Validation (서울) | 3,640 |

통화당 평균 1.44개 증상이 붙어 있습니다.

### 평가 지표와 제약

**Macro F1** = 9개 증상의 F1을 단순 평균한 값입니다. 증상별로 데이터 양이
크게 다른데(복통 838건 vs 두통 374건) Macro 평균은 **희귀한 증상도 같은
비중으로** 봅니다. 그래서 흔한 증상만 잘 맞혀도 점수가 오르지 않습니다.

**판정 임계값은 전 증상 0.5로 고정**입니다(주최측 지시). 모델이 내놓은 확률이
0.5 이상이면 "그 증상 있음"으로 판정합니다. 증상별로 다른 기준값을 쓰는 것은
금지입니다.

> **이 제약의 비용을 측정했습니다**: 증상별로 최적 임계값을 자유롭게 골랐다면
> 0.6441 → 0.6503 (**+0.0062**)까지 올라갔습니다. 즉 0.5 고정이 가져가는
> 손해가 0.006 정도이고, 그 이상은 확률 보정으로도 얻을 수 없습니다
> (단조 변환은 순위를 바꾸지 못하므로).

## 2. 데이터 분석 — 오차의 정체 (데이터 분석 내용)

**이 장이 이 작업의 가장 중요한 발견입니다.** 성능이 왜 0.66 부근에서
멈추는지를 모델 탓이 아니라 데이터로 설명합니다.

### 2-1. 모델이 놓친 것에는 애초에 근거가 없습니다

모델이 틀린 경우를 두 가지로 나눠, **전사 텍스트에 그 증상을 가리키는 표현이
실제로 있는지** 셌습니다.

| 증상 | 놓친 정답(FN) | 그중 전사에 표현이 있음 | 잘못 짚음(FP) | 그중 전사에 표현이 있음 |
|---|---:|---:|---:|---:|
| 구토 | 404건 | **1.5%** (6건) | 280건 | 50.4% |
| 두통 | 309건 | 10.4% | 240건 | 56.2% |
| 호흡곤란 | 210건 | 33.3% | 313건 | **86.9%** |

**읽는 법**: 구토를 놓친 404건 중 전사에 "토했다" 같은 표현이 있는 건 **6건**
뿐입니다. 모델이 읽고도 못 맞힌 게 아니라, **읽을 것이 없는데 라벨이 붙어
있습니다.** 반대로 호흡곤란을 잘못 짚은 313건 중 87%에는 "숨"이 나옵니다 —
모델은 텍스트를 제대로 읽었고, 라벨이 안 붙어 있었습니다.

→ 양쪽 모두 **모델의 독해력 문제가 아니라 어노테이션(라벨 부여) 방식의
문제**입니다. 전사 텍스트만으로는 복구할 수 없는 오차입니다.

### 2-2. '오심'은 질적으로 다릅니다

증상 표현이 전사에 **있는 통화만 모아서**, 그 안에서 라벨 유무를 구분할 수
있는지 측정했습니다(조건부 AUC. 0.5면 동전던지기, 1.0이면 완벽).

| 열상 | 고열 | 복통 | 호흡곤란 | 전신쇠약 | 두통 | 어지러움 | 구토 | **오심** |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 0.980 | 0.940 | 0.897 | 0.871 | 0.842 | 0.777 | 0.774 | 0.726 | **0.567** |

오심만 0.567로, 거의 **동전던지기**입니다. 더 구체적으로:

> 전사에 "메스꺼워요"가 또박또박 적혀 있어도 오심 라벨은 **63%만** 붙습니다.

오심의 전체 성적(AUC 0.777)은 대부분 "이게 구토·어지러움이 있는 통화인가"를
맞히는 데서 나오고, 그 안에서 오심이 추가로 붙었는지는 예측할 수 없습니다.

실제 최종 성적에서도 오심 F1이 **0.4101**로 9개 중 최하위입니다 — 모델
문제가 아니라 라벨 문제라는 측정 결과와 일치합니다.

### 2-3. 전사 길이는 충분합니다 (잘린 정보가 아닙니다)

"텍스트가 길어서 뒷부분이 잘려 성능이 낮은 것 아닌가"를 확인했습니다.

| | |
|---|---:|
| 토큰 길이 중앙값 | 230 |
| 95분위 | 460 |
| 모델 입력 한도 | 512 |
| 한도를 넘는 통화 | 788개 (2.7%) |
| 전체 토큰 중 버려지는 비율 | **0.8%** |
| 버려지는 구간에만 증상 근거가 있는 양성 | **1,115건 중 10건 (0.9%)** |

→ 잘려서 잃는 정보는 사실상 없습니다. 이 방향으로는 개선 여지가 없습니다.

## 3. 최종 모델 (모델 설명 ②)

### 3-1. 구조

**신경망 16개가 각자 9개 증상의 확률을 내고, 그 확률을 단순 평균한 뒤,
TF-IDF 선형모델의 확률을 10% 섞어서, 0.5 이상이면 증상 있음으로 판정합니다.**

```
최종 확률 = 0.9 × (신경망 16개 확률의 평균)  +  0.1 × (TF-IDF 확률)
판정      = 최종 확률 ≥ 0.5
```

### 3-2. 16개 멤버 구성 — 11개 계열

멤버들은 **일부러 서로 다르게** 만들었습니다. 같은 레시피로 16개를 만드는
것보다, 서로 다르게 틀리는 모델을 섞는 것이 더 좋다는 것을 측정했기
때문입니다(4장 참조).

| 계열 | 멤버 수 | 무엇이 다른가 |
|---|---:|---|
| base mean lr2e-5 | 2 | 기준 레시피 (학습률만 표기) |
| base attn lr2e-5 | 2 | 증상별 attention 헤드 |
| base mean lr3e-5 | 1 | 학습률 변경 |
| base attn lr3e-5 | 1 | 학습률 + 헤드 |
| base 정규화 텍스트 | 2 | 동의어를 통일한 입력 |
| base 도메인 적응 | 2 | 전사로 추가 사전학습 후 미세조정 |
| base CLS 풀링 | 1 | 문장 대표 벡터를 다르게 뽑음 |
| **large mean** | **2** | **더 큰 모델** (klue/roberta-large) |
| **large attn** | **1** | large + attention 헤드 |
| **large 정규화** | **1** | large + 동의어 통일 입력 |
| **large TAPT** | **1** | 도메인 적응 사전학습된 large |

- base = `klue/roberta-base` (110M 파라미터)
- large = `klue/roberta-large` (337M 파라미터)
- TAPT = `SangwonYoon/klue-roberta-large-tapt`

공통 학습 설정: 3 epoch · AdamW · bf16 · `pos_weight = clip(sqrt(음성/양성), 1, 5)` ·
**Training 29,200통화 전부 사용**.

> **용어 설명 (슬라이드에 넣을 때)**
> - **앙상블**: 여러 모델의 예측을 평균해 하나의 답을 내는 방식
> - **attention 헤드**: 증상마다 문장의 다른 부분에 주목하게 만든 구조
> - **도메인 적응(TAPT)**: 라벨 없이 전사 텍스트만으로 언어모델을 추가
>   학습시켜, 119 통화체에 익숙해지게 하는 단계
> - **TF-IDF + 로지스틱 회귀**: 단어·글자 조각의 등장 빈도만 보는 고전적
>   선형 모델. 딥러닝 모델이 흐릿하게 처리하는 드문 표현을 직접 잡아냅니다

### 3-3. 일부러 **쓰지 않은** 것

아래는 모두 측정해보고 **손해였기 때문에** 빼기로 결정한 것들입니다.
"단순한 평균"이 게으른 선택이 아니라 측정의 결과임을 보여주는 부분입니다.

| 쓰지 않은 기법 | 성능 변화 |
|---|---:|
| 증상별 임계값 | 규칙 위반 + 이득 미미 |
| 멤버별 가중치 (좋은 모델에 더 큰 비중) | −0.0013 |
| 증상별 혼합 비율 | −0.0004 |
| 스태킹 (메타 모델로 결합) | −0.033 |
| 멤버 선택 (성능 낮은 멤버 제거) | −0.0004 ~ −0.0007 |

공통 교훈: **조정할 수 있는 값을 늘리면 거의 항상 손해**였습니다. 5,840통화로
그 값을 맞추면 그 데이터에만 맞춰지고, 못 본 데이터에서는 이득이 사라집니다.

## 4. 무엇이 효과가 있었나 (결과 분석 ①)

약 **110회의 짝비교 실험**을 Training 내부의 5,840통화 홀드아웃에서
수행했습니다. 그중 성능을 올린 것은 **다섯 가지**입니다.

| 효과가 있었던 것 | 개선폭 | 검증 방식 |
|---|---:|---|
| **앙상블 (확률 단순 평균)** | **+0.0089** | 크기별 부분집합 150개 평균 |
| **large 계열 5개 추가** | +0.0037 (홀드아웃) | 반분 검증 240회 전승 |
| **이질 구성 (계열 섞기)** | +0.0016 | 무작위 조합 200개 중 200개 승 |
| **TF-IDF 10% 혼합** | +0.0012 | 반분 검증 80회, 91% 승 |
| **전체 데이터 학습** | +0.0010 | 데이터 크기 곡선 |

### 4-1. 가장 큰 효과: 앙상블 (+0.0089)

단일 모델은 약 0.638, 앙상블은 약 0.647입니다. 다른 어떤 기법보다 큰
차이이고, 이 과제에서 유일하게 반복적으로 통한 수단입니다.

### 4-2. 핵심 아이디어: **같은 수라도 "다르게" 섞는 것이 낫다**

앙상블은 모델을 10개쯤 넘으면 더 넣어도 오르지 않습니다
(10개 0.6462 / 16개 0.6463 / 23개 0.6462).

그래서 **수를 늘리는 대신 종류를 늘렸습니다.**

| 같은 6개 멤버인데 | Macro F1 | 멤버 간 예측 불일치 |
|---|---:|---:|
| 한 레시피로 6개 (seed만 다름) | 0.6448 | 0.0295 |
| **계열마다 하나씩 6개** | **0.6464** | **0.0358** |

멤버들의 개별 실력은 같습니다(0.6374 vs 0.6381). 차이는 **서로 얼마나 다르게
틀리는가**입니다. 무작위 조합 200번 중 **200번** 이질 구성이 이겼습니다.

### 4-3. large 계열 추가 — 제가 두 번 놓쳤던 것

`klue/roberta-large`는 처음에 "base와 비슷한데 3.7배 느리다"고 판단해 두 번
제외했습니다. **그 판단이 틀렸습니다.**

원인은 두 가지였습니다.
1. 학습 설정이 잘못된 상태로 측정했습니다(올바른 설정은 학습률 1.5e-5,
   batch 4×8). 올바르게 재측정하니 단독 0.6425로 base의 0.6378보다 명확히
   높았습니다.
2. **단독 성능으로 판단한 것 자체가 잘못**이었습니다. 단독 성능과 앙상블
   기여도의 상관은 **+0.22**뿐입니다 — 혼자 잘하는 모델이 팀에 기여한다는
   보장이 없습니다.

판단 기준을 "단독 점수"에서 **"앙상블에 넣었을 때의 변화"**로 바꾼 뒤
백본 후보 15개를 다시 측정했고, large 계열만 통과했습니다.

**멤버 수가 늘어서 오른 것이 아니라는 통제 실험**:

| 16개 구성에 무엇을 더하면 | 변화 | 반분 검증 승률 |
|---|---:|---:|
| **large 5개 추가** | **+0.0019** | **98%** |
| 기존 멤버 3개를 복제해 추가 | **−0.0012** | **0%** |

같은 수를 더하는데 부호가 반대입니다. 효과는 "수"가 아니라 **"새로운 종류"**에서
나옵니다.

## 5. 왜 이 버전을 제출하는가 (결과 분석 ②)

> **이 장이 "여러 모델 중 왜 이걸 골랐나"에 대한 답입니다.**

### 5-1. 후보 네 가지를 모두 Validation에서 실측했습니다

| 구성 | Macro F1 | 모델 수 | 파라미터 | 추론 시간 | 용량 |
|---|---:|---:|---:|---:|---:|
| **16개 fp16 (제출)** | **0.65746** | 16 | 2,903M | 6.1분 | 5.82 GB |
| 증류 학생 6개 | 0.65683 | 6 | 1,342M | ~3.3분 | ~2.1 GB |
| large 5개만 | 0.65680 | 5 | 1,685M | 3.7분 | 3.39 GB |
| base 11개 | 0.65658 | 11 | 1,219M | 2.9분 | 4.89 GB |

### 5-2. **점수로는 네 개가 구분되지 않습니다**

차이가 최대 0.0009인데, 3,640통화에서 점수 자체의 불확실성이 **±0.0059**
입니다(부트스트랩 4,000회).

| 구성 | 실측 | 95% 신뢰구간 |
|---|---:|---|
| 16개 fp16 | 0.65746 | [0.64554, 0.66886] |
| 증류 학생 6개 | 0.65683 | [0.64485, 0.66780] |
| large 5개 | 0.65680 | [0.64467, 0.66794] |
| base 11개 | 0.65658 | [0.64488, 0.66772] |

Validation을 반으로 갈라 500번 재보니 1위를 차지한 비율이
16개 36% / large5 28% / 학생6 18% / 11개 18%로 갈렸고,
**양쪽 반쪽 모두에서 16개가 1위였던 경우는 4%**뿐입니다.

→ "16개가 가장 좋다"는 **주장할 수 없습니다.** 네 구성은 통계적으로 같습니다.

### 5-3. 그래서 점수가 아닌 기준으로 골랐습니다

| 기준 | 판단 |
|---|---|
| **검증 완료 여부** | 16개 fp16은 7개 항목 점검을 통과했습니다 — 오프라인 적재, 오프라인 추론, CSV 규격, 파일명 일치, 증상 목록 범위. 압축파일 CRC 검사도 통과. 나머지 후보는 미검증 또는 미조립 |
| **견고함** | 멤버가 많을수록 하나가 어긋나도 영향이 1/16로 작습니다. 또 16개는 **이미 검증된 11개 구성을 그대로 포함**하므로, large 멤버에 문제가 생겨도 점수가 서서히 떨어질 뿐 무너지지 않습니다 |
| **기대값** | 부트스트랩 평균(0.65714)과 반쪽 1위 비율(36%) 모두 네 후보 중 가장 높습니다 |
| **용량 위험** | fp32 원본은 11.62 GB입니다. fp16 저장으로 5.82 GB로 줄였습니다 |

**선택 근거를 한 줄로**: *"점수가 같으므로, 검증이 끝났고 가장 견고한 것을
골랐다."*

### 5-4. fp16 저장에 대해 (질문 나올 수 있는 부분)

가중치를 16비트로 저장해 **용량을 정확히 절반**으로 줄였습니다
(11.62 GB → 5.82 GB).

- **연산 정밀도와는 무관합니다.** 추론 코드가 모델을 32비트로 만든 뒤 값을
  불러오는데, 이 과정에서 32비트로 되돌아갑니다. 채점 환경이 16비트 연산을
  지원하는지와 관계없고, CPU에서도 동일하게 동작합니다.
- **성능 영향을 측정했습니다**: Validation 32,760개 판정 중 **라벨이 달라진
  것은 2건**, Macro F1 차이는 +0.00003입니다(32비트 0.65743 / 16비트 0.65746).
  이 차이는 잡음입니다.

## 8. 사회안전 시사점 (출제문제 요구 항목)

### 8-1. 이 기술이 현장에서 쓰일 수 있는 방식

119 신고 접수 중 대화만으로 환자 증상을 자동 분류하면,

- **출동 전 준비**: 호흡곤란·열상처럼 처치 장비가 갈리는 증상을 미리
  알려 구급대가 장비를 준비할 수 있습니다. 측정 성적도 이 두 증상에서
  높습니다(호흡곤란 0.667, 열상 0.889).
- **중증도 판단 보조**: 복통·고열 같은 빈도 높은 증상의 자동 기록으로
  접수자의 입력 부담을 줄입니다.
- **사후 통계**: 지역·시간대별 증상 분포를 자동 집계해 자원 배치에 활용.

### 8-2. 그러나 **단독 판단 근거로 쓰면 안 됩니다** — 측정 근거

이 작업에서 가장 중요한 안전 관련 발견입니다.

1. **놓친 증상의 대부분은 전사에 근거가 없습니다.** 구토를 놓친 404건 중
   전사에 표현이 있는 것은 6건(1.5%)뿐입니다. 즉 **대화에 나오지 않은 증상은
   어떤 모델도 알 수 없습니다.** 자동 분류를 "증상이 없다"의 근거로 쓰면
   위험합니다.

2. **증상별 신뢰도가 크게 다릅니다.** 열상 F1 0.889와 오심 F1 0.410은
   같은 시스템의 출력이지만 신뢰 수준이 전혀 다릅니다. 현장에 쓸 때는
   **증상별로 다른 취급**이 필요합니다.

3. **라벨 자체가 불확실한 영역이 존재합니다.** "메스꺼워요"가 명확히
   기록돼 있어도 오심 라벨은 63%만 붙었습니다. 사람 사이에서도 판단이
   갈리는 영역이며, 자동화가 그 불일치를 해소해주지는 않습니다.

→ **권고**: 보조 도구(접수자에게 후보를 제안하고 확인받는 방식)로 쓰고,
증상별 신뢰도를 함께 표시하며, "미검출"을 "없음"으로 해석하지 않도록
설계해야 합니다.

### 8-3. 데이터 품질 개선이 모델 개선보다 효과적입니다

약 110회의 실험에서 모델·손실함수·전처리 쪽으로 얻은 개선은 대부분 0이었고,
오차의 주된 원인은 라벨 불확실성이었습니다. 실무적으로는 **어노테이션 기준을
명확히 하는 것**(특히 오심/구토/어지러움의 구분)이 모델 개선보다 큰 성능
향상을 가져올 가능성이 높습니다.

## 부록 A. 측정 방법 — 왜 이 숫자들을 믿을 수 있는가

PPT에 한 장 넣으면 실험의 신뢰도를 보여줄 수 있습니다.

| 원칙 | 내용 |
|---|---|
| **Validation 분리** | 모든 설계 결정은 Training 내부 5,840통화 홀드아웃에서 했습니다. 공식 Validation은 **제출 결정 시점에만** 측정했습니다 |
| **짝비교** | seed만 바꿔도 성능이 0.0023 흔들리므로, 한 번의 실행으로 결론 내지 않고 같은 seed끼리 짝지어 비교했습니다 |
| **반분 검증** | 데이터를 반으로 갈라 한쪽에서 고르고 **다른 쪽에서 측정**했습니다. 이 방법으로 "홀드아웃에서는 좋아 보이는데 실제로는 손해"인 기법 여러 개를 걸러냈습니다 |
| **부트스트랩** | 차이가 잡음과 구분되는지 신뢰구간으로 확인했습니다 |
| **재현 검증** | 측정 경로 자체를 검증했습니다 — 기존 11개 구성을 다시 채점해 0.65658이 **정확히 재현**되는 것을 확인한 뒤 새 숫자를 믿었습니다 |

**선택 편향을 실제로 측정한 예**: 홀드아웃에서 "최적의 5개 조합"을 고르면
0.65231이 나오지만, 고르는 것까지 반쪽 데이터 안에서 하고 다른 쪽에서 재면
0.64921입니다. **차이 +0.0031이 순수한 선택 편향**입니다. 이 때문에
"성능 좋은 조합 찾기"를 모두 기각했습니다.
